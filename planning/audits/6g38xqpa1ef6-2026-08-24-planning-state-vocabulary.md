## Findings

#### H1. Offset desynchronization in `SetFindingStatus` corrupts markdown on files with code fences  · **Status:** fixed

**File:** `internal/domain/finding.go:73-82,275`, `internal/core/finding.go:229` | **Component:** domain/finding
**Effort:** S · **Urgency:** acute

`ParseFindings` strips code fences via `fenceRe.ReplaceAllString(body, "")` before locating finding headers and computing `f.StatusSpan`. The resulting `Span{Start, End}` byte offsets are computed relative to the stripped string (`prose`), not the raw file body.

When `SetFindingStatus` performs the status rewrite:
```go
return body[:f.StatusSpan.Start] + want + body[f.StatusSpan.End:], nil
```
it applies the stripped offsets directly to the original, un-stripped `body`. If an audit file contains any fenced code block preceding a finding — such as the standard scaffold template generated by `tskflwctl audit new` or fenced code examples in finding descriptions — the byte offsets are misaligned by the length of the stripped fences.

As demonstrated in testing, running `tskflwctl audit finding <slug> <code/slug> --status fixed` on an audit with a template fence overwrites arbitrary characters inside the template block (e.g. converting `<minimum fix>` into `<minimfixedix>`) while leaving the actual finding's status untouched.

**Recommendation:** Make `ParseFindings` fence-aware line-by-line (matching `scanAcceptanceCheckboxes` / `fenceScanner`), or compute byte offsets against the original `body` without stripping text so that `StatusSpan` remains valid for body slicing.

#### H2. Interactive `$EDITOR` writes bypass write-time ID validation (`task edit` allows invalid Crockford IDs)  · **Status:** fixed

**File:** `internal/store/frontmatter.go:88-123`, `internal/store/edit.go:60-74`, `internal/store/fsstore.go:379-397` | **Component:** store/frontmatter
**Effort:** XS · **Urgency:** acute

`updateFrontmatter` only executes `validateIDUpdate(updates)` for keys present in the `updates` map. When an entity is edited interactively using `$EDITOR` (`task edit`, `audit edit`, `epic edit`), the user modifies the raw YAML frontmatter directly.

In `editFile`, the edited text is passed to `parseTask`, which unmarshals the YAML into `domain.Task` but does not validate that `t.ID` satisfies `id.Valid()`. `editFile` then calls `updateFrontmatter` with only `map[string]any{"updated_at": ...}`. Because `"id"` is not present in `updates`, `validateIDUpdate` returns `nil`. `writeFileAtomic` subsequently writes the invalid Crockford ID (e.g. containing `l` or `u`) directly to disk. The claim that `updateFrontmatter` is "the single choke point every write passes through" fails for interactive editor sessions.

**Recommendation:** Validate `id.Valid(t.ID)` in `parseTask`, `parseAudit`, and `parseResearch`, or parse and validate the YAML `id` scalar inside `updateFrontmatter` / `splitFrontmatterStrict`.

#### M1. `SetFindingStatus` bypasses OCC / CAS conflict handling and uses interactive editor loop semantics  · **Status:** tracked by 6g392b0rps7w

**File:** `internal/core/finding.go:220-232`, `internal/store/edit.go:31-100` | **Component:** core/finding
**Effort:** S · **Urgency:** soon

Unlike all other programmatic mutations in `core.Service` (`AppendAuditBody`, `MoveAudit`, `SetTaskFields`, `SetCriterionState`, etc.), which perform compare-and-swap (CAS) content-hash verification and wrap execution in `retryOnConflict(s, dryRun, func() ...)`, `SetFindingStatus` routes through `store.EditAudit`.

`store.EditAudit` uses `editFile`, which was designed for interactive human `$EDITOR` sessions. `editFile` acquires an advisory flock only after parsing and does not verify content hashes or re-check CAS before writing, risking lost updates under concurrent automated edits. To prevent `editFile` from re-prompting on parse failures, `SetFindingStatus` uses a closure boolean flag (`attempted := false`) rather than proper OCC retry.

**Recommendation:** Add a dedicated, non-interactive `SetFindingStatus` method to `store.FS` that checks content hashes, holds advisory locks during read-modify-write, and wraps the operation in `retryOnConflict`.

#### M2. `CriterionJSON` wire DTO omits `State` and `Reason` for machine consumers  · **Status:** fixed

**File:** `internal/wire/dto.go:85-99`, `internal/cli/task.go:400-408` | **Component:** wire/dto
**Effort:** XS · **Urgency:** soon

Schema 1.45 added `ACJSON.Explained` to `TaskInfoJSON` and `task info --json`, and `render.AcceptanceHuman` displays criterion state and explanation in the CLI checklist. However, `wire.CriterionJSON` was not updated to carry these fields and only defines `Index`, `Checked`, and `Text`.

Machine consumers and AI agents calling `tskflwctl task ac <slug> --list --json` cannot inspect which criteria are `deferred`, `wontfix`, or `n/a`, nor access the associated reasons.

**Recommendation:** Add `State string `json:"state,omitempty"` and `Reason string `json:"reason,omitempty"` to `CriterionJSON` in `internal/wire/dto.go` and map them in `ToCriteriaJSON`.

#### M3. Leftmost matching in `criterionSuffixRe` breaks positional authority on multi-marker criteria  · **Status:** fixed

**File:** `internal/domain/body.go:423-452` | **Component:** domain/body
**Effort:** S · **Urgency:** soon

The regex `criterionSuffixRe` (`(?i)[ \t]*·[^*\p{L}\p{N}]*\*\*([^:*]+):\*\*[ \t]*(.*)$`) is documented as anchored to the last marker on the line. However, because RE2 regex matching is leftmost-longest, a criterion line containing an earlier middle-dot bold marker (e.g. `- [ ] Tests · **Coverage:** 100% · **deferred:** waiting on harness`) matches at the first marker (`· **Coverage:**`) rather than the trailing suffix.

Because `ParseCriterionState("Coverage")` returns false, `splitCriterion` treats the entire line as ordinary text, silently ignoring the trailing deferral. Consequently, `CountAcceptanceCriteria` omits the explained count, `task ac` misclassifies the state as unmet, and `SetCriterionState` strips the earlier bold text when updating the line.

**Recommendation:** Match suffix markers from the end of the line or scan right-to-left across `·` separators to ensure only the trailing disposition suffix is matched.

#### L1. Unsanitized newline injection in `SetCriterionState` and `SetFindingStatus`  · **Status:** fixed

**File:** `internal/domain/body.go:253-255`, `internal/domain/finding.go:250-258` | **Component:** domain/body
**Effort:** XS · **Urgency:** eventually

Neither `SetCriterionState` (`reason`) nor `SetFindingStatus` (`status`/decoration) validates against or strips embedded newline characters (`\n`). Passing a multi-line string through `--reason` or `--status` injects raw newlines into the markdown list item or finding header, corrupting markdown formatting and potentially injecting phantom checkbox items.

**Recommendation:** Reject or strip newlines from `reason` in `SetCriterionState` and decoration in `SetFindingStatus`.

#### L2. Discrepancy between `stripLeadingDecoration` and regex decoration matching  · **Status:** fixed

**File:** `internal/domain/resolution.go:96-106`, `internal/domain/body.go:423` | **Component:** domain/resolution
**Effort:** XS · **Urgency:** eventually

`stripLeadingDecoration` uses `r < 0x2000` to find non-symbol runes, which treats accented Latin letters, Greek, Cyrillic, Hebrew, and Arabic characters as token characters while skipping runes `>= 0x2000` (e.g. emojis). In contrast, `criterionSuffixRe` uses `[^*\p{L}\p{N}]*`. The two functions implement different heuristics for what constitutes leading decoration.

**Recommendation:** Align decoration stripping to use standard Unicode properties (`unicode.IsLetter` / `unicode.IsDigit` or `\p{L}\p{N}`).

#### L3. `TestSharedResolutionWordsAgree` is tautological and cannot prevent vocabulary drift  · **Status:** fixed

**File:** `internal/domain/resolution_test.go:12-29`, `internal/domain/resolution.go:23-30` | **Component:** domain/resolution
**Effort:** XS · **Urgency:** eventually

`TestSharedResolutionWordsAgree` asserts that the hardcoded slice `SharedResolutionWords()` (`{"deferred", "wontfix"}`) is present in both `FindingStatuses()` and `CriterionStates()`. Because it only tests the two words listed in the constant slice, any new resolution status added to either findings (such as `superseded`) or criteria (such as `n/a`) is not validated for mutual consistency, leaving the vocabularies vulnerable to unmonitored drift.

**Recommendation:** Maintain a comprehensive bidirectional matrix test across all finding and criterion statuses to document and enforce intended overlaps and intentional differences.
